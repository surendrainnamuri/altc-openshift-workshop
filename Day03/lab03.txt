LAB 03 - BUILD AN EVENT-READY OPENSHIFT CI/CD PIPELINE

Lab type: Progressive, attendee-focused hands-on practice
Recommended duration: 150-210 minutes in full
Difficulty: Foundation to intermediate

======================================================================
1. LAB PURPOSE
======================================================================

You will create and operate a small Tekton pipeline on OpenShift Container Platform. The safe core path uses locally created Tasks and a shared workspace, so it does not depend on a public Git repository or privileged image builder. You will then inspect PipelineRun/TaskRun relationships, create an optional BuildConfig integration, design a secure webhook path, and evaluate Service Binding availability.

The lab separates core exercises from optional environment-dependent exercises. Complete only actions authorised on your cluster.

Core delivery model:

PipelineRun
  -> prepare-source Task writes a simulated source revision
  -> test-source Task reads and validates it
  -> package-result Task records an artifact identity
  -> finally summary Task executes

Extension model:

Git webhook -> EventListener -> TriggerBinding -> TriggerTemplate -> PipelineRun
Pipeline Task -> BuildConfig -> Build -> image
Application + backing service -> ServiceBinding -> projected configuration

======================================================================
2. LEARNING OUTCOMES
======================================================================

After completing this lab, you should be able to:

1. Discover OpenShift Pipelines and Trigger APIs.
2. Create parameterised Tekton Tasks.
3. connect Tasks through a workspace and results.
4. Create and execute a PipelineRun.
5. Trace a PipelineRun to TaskRuns and pods.
6. Diagnose a controlled Task failure.
7. Explain safe retry and cancellation.
8. Decide whether BuildConfig or a Tekton-native build owns image creation.
9. Design and optionally create Git trigger resources.
10. Discover and assess Service Binding support.

3. PREREQUISITES AND SAFETY
======================================================================

Required:

- OpenShift project creation or access to an assigned project.
- `oc` CLI.

- Permission to create Task, Pipeline, TaskRun, PipelineRun, ConfigMap, Secret, and PVC resources in the assigned namespace.

Optional extensions require additional permissions, cluster APIs, network access, a storage class, and/or a Git repository you control.

- Do not grant cluster-admin or broad wildcard RBAC.
- Do not expose an EventListener publicly without authentication, TLS, and authorisation.
- Use only approved images.
- Replace placeholders before running commands.
- Do not run cleanup in a namespace you did not create or receive explicitly.

5. LAB 1 - CREATE FOUR TASKS
======================================================================

Step 1.1 - Create prepare-source-task.yaml

apiVersion: tekton.dev/v1
kind: Task
metadata:
  name: prepare-source
spec:
  params:
  - name: git-revision
    type: string
  workspaces:
  - name: source
  results:
  - name: resolved-revision
    description: Revision used by this simulated source preparation.
  steps:
  - name: prepare
    image: registry.access.redhat.com/ubi9/ubi-minimal:latest
    workingDir: $(workspaces.source.path)
    script: |
      #!/usr/bin/env bash
      set -euo pipefail
      printf '%s\n' 'sample application source' > application.txt
      printf '%s\n' '$(params.git-revision)' > revision.txt
      printf '%s' '$(params.git-revision)' > '$(results.resolved-revision.path)'
      echo 'Prepared source files'

This Task simulates cloning so the core lab remains deterministic. In a real pipeline, use a reviewed Git clone Task and emit the resolved full commit SHA.

Step 1.2 - Create test-source-task.yaml

apiVersion: tekton.dev/v1
kind: Task
metadata:
  name: test-source
spec:
  params:
  - name: expected-text
    type: string
    default: sample
  workspaces:
  - name: source
  results:
  - name: test-outcome
  steps:
  - name: test
    image: registry.access.redhat.com/ubi9/ubi-minimal:latest
    workingDir: $(workspaces.source.path)
    script: |
      #!/usr/bin/env bash
      set -euo pipefail
      grep -F -- '$(params.expected-text)' application.txt
      printf '%s' 'passed' > '$(results.test-outcome.path)'
      echo 'Source validation passed'

Step 1.3 - Create package-result-task.yaml

apiVersion: tekton.dev/v1
kind: Task
metadata:
  name: package-result
spec:
  params:
  - name: revision
    type: string
  - name: test-outcome
    type: string
  results:
  - name: artifact-reference
  steps:
  - name: record
    image: registry.access.redhat.com/ubi9/ubi-minimal:latest
    script: |
      #!/usr/bin/env bash
      set -euo pipefail
      test '$(params.test-outcome)' = 'passed'
      ref='example.invalid/day03/app:$(params.revision)'
      printf '%s' "${ref}" > '$(results.artifact-reference.path)'
      echo "Recorded non-pushed lab artifact ${ref}"

The `example.invalid` domain deliberately prevents accidental pushes. A production build must emit a real immutable digest, not only a tag.

Step 1.4 - Create run-summary-task.yaml

apiVersion: tekton.dev/v1
kind: Task
metadata:
  name: run-summary
spec:
  params:
  - name: message
    type: string
  steps:
  - name: print
    image: registry.access.redhat.com/ubi9/ubi-minimal:latest
    script: |
      #!/usr/bin/env bash
      printf '%s\n' '$(params.message)'

Step 1.5 - Apply and inspect

oc apply -f prepare-source-task.yaml
oc apply -f test-source-task.yaml
oc apply -f package-result-task.yaml
oc apply -f run-summary-task.yaml
oc get task

oc describe task/prepare-source

Checkpoint questions

- Which data is passed as a parameter?
- Which files cross Tasks through the workspace?
- Which small values are emitted as results?
- Why is the image reference not a real release artifact?

6. LAB 2 - CREATE THE PIPELINE
======================================================================

Create day03-ci-pipeline.yaml:

apiVersion: tekton.dev/v1
kind: Pipeline
metadata:
  name: day03-ci
spec:
  params:
  - name: git-revision
    type: string
    default: main
  - name: expected-text
    type: string
    default: sample
  workspaces:
  - name: shared-data
  results:
  - name: resolved-revision
    value: $(tasks.prepare.results.resolved-revision)
  - name: artifact-reference
    value: $(tasks.package.results.artifact-reference)
  tasks:
  - name: prepare
    taskRef:
      name: prepare-source
    params:
    - name: git-revision
      value: $(params.git-revision)
    workspaces:
    - name: source
      workspace: shared-data
  - name: test
    taskRef:
      name: test-source
    runAfter:
    - prepare
    params:
    - name: expected-text
      value: $(params.expected-text)
    workspaces:
    - name: source
      workspace: shared-data
  - name: package
    taskRef:
      name: package-result
    params:
    - name: revision
      value: $(tasks.prepare.results.resolved-revision)
    - name: test-outcome
      value: $(tasks.test.results.test-outcome)
  finally:
  - name: summary
    taskRef:
      name: run-summary
    params:
    - name: message
      value: Day03 pipeline reached its final reporting task.

Apply:

oc apply -f day03-ci-pipeline.yaml
oc get pipeline/day03-ci -o yaml

Reason about the graph before running:

- `test` explicitly runs after `prepare` and shares its files.
- `package` consumes results from both tasks, so data dependencies order it.
- `summary` is a finally task.

Checkpoint: Predict which TaskRuns will exist if `test` fails.

Resolver extension

Inspect the supplied tasks and resolver support without changing cluster configuration:

oc get task/git-clone -n openshift-pipelines -o yaml
oc get task/buildah -n openshift-pipelines -o yaml
oc get task/openshift-client -n openshift-pipelines -o yaml

If a named Task is not present, record that result; cluster administrators can disable automatic resolver tasks. Do not copy a task into your project without reviewing its images, parameters, workspaces, results, and security requirements.

Sketch how the pipeline's `taskRef` would change to use the cluster resolver with parameters `kind=task`, `name=<task-name>`, and `namespace=openshift-pipelines`. Keep the deterministic Tasks for the core execution unless the workshop environment explicitly supports the full documented build flow.

7. LAB 3 - EXECUTE A SUCCESSFUL PIPELINERUN
======================================================================

Step 3.1 - Create day03-ci-run.yaml

apiVersion: tekton.dev/v1
kind: PipelineRun
metadata:
  generateName: day03-ci-
  labels:
    app.kubernetes.io/name: day03-sample
spec:
  pipelineRef:
    name: day03-ci
  params:
  - name: git-revision
    value: commit-a1b2c3d
  - name: expected-text
    value: sample
  workspaces:
  - name: shared-data
    volumeClaimTemplate:
      spec:
        accessModes:
        - ReadWriteOnce
        resources:
          requests:
            storage: 100Mi

Create it:

oc create -f day03-ci-run.yaml

Capture the generated name:

If the PVC remains Pending because no dynamic storage is available, ask for an assigned PVC or replace the workspace binding with `emptyDir: {}` if supported and appropriate for this single-node-sequence lab. Do not alter cluster storage.

Answer:

2. Which step returned non-zero?

Recovery

11. LAB 7 - OPTIONAL GIT WEBHOOK DESIGN
======================================================================

This section is design-first. Create live external webhooks only in a repository you control and only if your EventListener can be exposed securely.

Step 7.1 - Map event data

For a GitHub-style push payload, propose:

git-url       <- $(body.repository.clone_url)
git-revision  <- $(body.after)
git-ref       <- $(body.ref)
delivery-id   <- provider request header or $(context.eventID)

Step 7.2 - Define controls

Your design must:

- Verify the provider signature with a Secret.
- Accept only the required event type.
- Accept only the intended repository and refs/heads/main.
- Pass the exact commit SHA.
- Use a TriggerTemplate with generateName.
- Use a separate EventListener ServiceAccount with only create PipelineRun permission.
- Use TLS and avoid secrets in URLs or logs.

Step 7.3 - Discover installed syntax

oc explain eventlistener.spec --recursive
oc explain triggerbinding.spec --recursive
oc explain triggertemplate.spec --recursive

Compare the cluster API with Topic05 before applying YAML. Trigger/interceptor syntax is version-sensitive.

For an OpenShift Pipelines 1.22 cluster, expect `triggers.tekton.dev/v1`. A documented TriggerTemplate creates a tekton.dev/v1 PipelineRun, selects its identity under `spec.taskRunTemplate.serviceAccountName`, and can create isolated storage with a `volumeClaimTemplate`.

Secure exposure design

Prefer an OpenShift re-encrypt TLS Route for an externally reachable EventListener. Record how the router validates the destination service certificate. Do not fall back to an insecure HTTP Route merely to make the exercise pass.

Step 7.4 - Acceptance tests

Document expected outcomes:

Valid signed main push: exactly one run
Invalid signature: no run
Valid feature branch push: no run
Duplicate delivery ID: no duplicate side effect

Evidence should include the provider delivery record, EventListener logs without secrets, and PipelineRun labels/annotations.
