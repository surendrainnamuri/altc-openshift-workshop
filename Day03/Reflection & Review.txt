REFLECTION & REVIEW - CI/CD EXERCISE AND REVIEW DISCUSSION

Purpose

This attendee-led review consolidates Day03 into one delivery story. You will explain the resources, inspect evidence from a run, diagnose realistic failures, and decide how to improve the workflow. Use it after completing Lab03 or as a future recall guide.

Recommended duration: 60-90 minutes
Suggested format: Individuals or groups of two or three

Learning outcomes

You should be able to:

- Trace Git event -> Trigger -> PipelineRun -> TaskRuns -> pods -> image -> deployment.
- Explain where BuildConfig fits when it is used.
- Distinguish configuration inputs, shared files, results, credentials, and artifacts.
- Interpret a failed run using conditions, logs, and events.
- Identify security and reproducibility risks.
- present a concise CI/CD evidence report.

PART 4 - FAILURE SCENARIOS
======================================================================

For each scenario, state the first three checks, likely fault domain, safe correction, and proof of recovery.

Scenario A: PipelineRun exists but no TaskRun starts

Consider definition resolution, missing parameters/workspaces, admission, Pipeline validation, and ServiceAccount.

Scenario B: clone TaskRun pod remains Pending

Consider unbound PVC, quota, scheduling, security constraints, and image pull. Events are likely more useful than Git logs.

Scenario C: webhook reports success but no run appears

Consider interceptor filtering, binding field paths, TriggerTemplate validation, EventListener identity, namespace, and provider delivery ID.

Scenario D: two runs start for one push

Consider provider redelivery, two matching triggers, BuildConfig plus Tekton webhooks, and missing deduplication.

Scenario E: pipeline is green but staging runs old code

Consider mutable tags, racing runs, ImageStream trigger behaviour, incorrect result wiring, and rollout status.

Scenario F: application cannot connect after a ServiceBinding is created

Consider CRD/API mismatch, binding readiness, projected key names, workload restart, NetworkPolicy, TLS, and credential validity. Do not print the Secret.

======================================================================
PART 5 - PIPELINE DESIGN REVIEW
======================================================================

Review the pipeline against these questions:

Reproducibility

- Is source resolved to a full commit SHA?
- Are task and tool images reviewed and pinned?
- Is the release artifact recorded by digest?
- Does promotion reuse rather than rebuild the artifact?

Security

- Does the run use a dedicated least-privilege ServiceAccount?
- Are secrets absent from params, results, logs, and Git?
- Are external webhooks authenticated, filtered, and TLS protected?
- Can untrusted pull request code reach deployment credentials?

Reliability

- Are timeouts defined?
- Are repeated operations idempotent?
- Are concurrent runs isolated?
- Do finally tasks tolerate partial execution?

Operability

- Can a responder find the first failed TaskRun quickly?
- Are run, commit, image, and environment correlated?
- Are retention and durable evidence policies defined?
- Are rollback boundaries understood?

For every "No" or "Unknown", write one concrete improvement and an owner.

======================================================================
PART 6 - CONCEPT REVIEW QUESTIONS
======================================================================

1. Why is a Pipeline not itself a running CI/CD job?
2. What is the relationship between PipelineRun and TaskRun?
3. When is `runAfter` useful, and when is a result dependency clearer?
4. What is the difference between a BuildConfig and a Build?
5. Why can an ImageChange trigger be both valuable and risky?
6. Which object extracts values from a webhook body?
7. Which object describes the PipelineRun that an event should create?
8. Why must signature verification happen before payload trust?
9. What remains external after a PipelineRun is deleted?
10. Why does service binding simplify configuration but not remove security obligations?

Suggested answer themes

1. It is a reusable desired-state definition; PipelineRun executes it.
2. PipelineRun coordinates the graph and creates TaskRuns for tasks.
3. runAfter is an explicit control dependency; result use expresses data and order together.
4. BuildConfig is the recipe; Build is one execution.
5. It propagates patched bases but also introduces a new untested change.
6. TriggerBinding, often after an interceptor validates/transforms the event.
7. TriggerTemplate.
8. Payload fields can be forged.
9. Pushed images, external artifacts, deployments, and external side effects follow their own lifecycle.
10. Bound data can contain credentials and still requires RBAC, rotation, TLS, and safe consumption.

======================================================================
PART 7 - CAPSTONE DISCUSSION
======================================================================

Scenario

An organisation has 80 microservices. Every team copies pipeline YAML, uses `latest`, and has a Git webhook with broad deployment credentials. Builds are fast, but incidents are difficult to trace and duplicated runs are common.

Propose a staged improvement plan:

Immediate risk reduction:

- Separate CI and deployment identities.
- Protect and filter webhooks.
- record commit SHA and image digest.
- prevent untrusted PRs from accessing release credentials.

Standardisation:

- Publish reviewed reusable Tasks/Pipelines through supported resolvers or versioned bundles.
- define common labels, results, timeouts, and evidence.
- use parameterised definitions rather than copied forks.

Governance:

- Add policy checks, approvals by environment risk, retention, and provenance.
- Make promotion use the tested digest.
- measure reliability without encouraging teams to bypass checks.

Operational maturity:

- Centralise allowed task/tool images.
- provide dashboards and failure taxonomies.
- test disaster recovery, credential rotation, and rollback.
