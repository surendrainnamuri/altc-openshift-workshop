⭐ Understanding Projects, Services, and Routes in OpenShift
These three concepts form the foundation of how applications are organised, accessed, and exposed inside an OpenShift cluster.
They are also the first things your workshop attendees will interact with in the Developer Sandbox.

🧩 1. Projects — Secure, Isolated Workspaces
What is a Project?
A Project in OpenShift is a secure, isolated namespace that groups all related Kubernetes/OpenShift resources for an application or team.

It is similar to a Kubernetes namespace but with additional OpenShift features:

Built‑in RBAC (Role-Based Access Control)

Quotas and limits

Network isolation

Default security policies

Integrated developer workflows

Why Projects matter
Projects ensure:

Multi-tenancy — each team/app gets its own isolated environment

Security — resources cannot cross boundaries without permissions

Organisation — everything for an app lives in one place

Access control — you can assign users to specific projects

Common commands
Code
oc new-project myapp
oc project myapp
oc get projects
Workshop analogy
A Project is like a folder in your laptop — everything for your application lives inside it.

🧩 2. Services — Stable Internal Access to Pods
What is a Service?
A Service provides a stable network endpoint to access a group of Pods.

Pods are ephemeral — they come and go.
A Service ensures your application always has a consistent IP and DNS name.

Why Services matter
They load-balance traffic across Pods

They provide stable connectivity even when Pods restart

They enable internal communication between microservices

They abstract Pod IPs

Types of Services
ClusterIP (default) — internal-only

NodePort — exposes on node ports

LoadBalancer — cloud load balancer

ExternalName — DNS alias

Common commands
Code
oc get svc
oc expose deployment myapp
Workshop analogy
A Service is like a reception desk — no matter which employee (Pod) is available, the desk routes you to the right one.

🧩 3. Routes — External Access to Applications
What is a Route?
A Route exposes a Service outside the cluster using an HTTP/HTTPS endpoint.

It is OpenShift’s enhanced version of Kubernetes Ingress.

Why Routes matter
They allow external users to access your application

They support TLS termination (edge, passthrough, re-encrypt)

They integrate with OpenShift’s HAProxy router

They provide custom hostnames

Common commands
Code
oc expose svc/myapp
oc get routes
Route example
A route might look like:

Code
http://myapp-myproject.apps.cluster.example.com
Workshop analogy
A Route is like a public website URL — it lets anyone outside the building reach your application.

🔗 How They Work Together (Simple Flow)
Code
Pods → Service → Route → External Users
Step-by-step
You deploy an application → Pods are created

You expose the deployment → A Service is created

You expose the Service → A Route is created

Users access the application via the Route URL

This is the standard OpenShift workflow for exposing applications.

🧠 Visual Summary (Trainer-Friendly)
Concept		Purpose			Scope		Example
Project		Isolated workspace	Cluster-wide	myproject
Service		Stable internal access	Inside cluster	myapp-service

🎯 Trainer’s Closing Line
Projects organise your applications, Services connect them internally, and Routes expose them externally.
Together, they form the backbone of how applications live and communicate in OpenShift.
